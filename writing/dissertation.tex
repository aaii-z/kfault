\noindent {{\huge \bf Abstract}}\\
%%%%%%%%%%%%
This project separates CUDA kernels that are genuinely correct from those that
only pass the benchmark. KernelBench scores a generated kernel against a
reference PyTorch module on five random, contiguous inputs. That test is kept, at a tighter tolerance, and
stress tests are added that change the memory layout of the inputs, their size
and type, and repeat the call. Kernels that pass the benchmark but fail
under stress are counted as silent failures. The stress tests are hidden from
the repair loop, so the model cannot learn to satisfy them. Applied to 100 problems across
three models, with reasoning on and off on the same weights, and on two GPUs,
this yields 2,852 kernel attempts. Repair raises the
share the benchmark accepts in every condition, by up to 43 points, and the
share of those that are silently wrong with it.
Of the 244 kernels repair turns into a benchmark success, 79 are silent
failures, twice as often as among kernels accepted first time, 25.7\% against
12.4\%. After repair, KernelBench detects no
significant difference between the three models, while the stress tests still
separate them. A repaired kernel is not reliably more correct; it is reliably
harder to catch.

\section{Introduction}

\subsection{Motivation}

Machine learning depends on a small amount of code that almost nobody writes. A
GPU kernel is the layer where a mathematical operation becomes instructions on
hardware, and writing one well takes expert knowledge of memory hierarchies and
thread scheduling. FlashAttention, one of the most consequential kernels of the
last decade, arrived five years after the architecture it accelerates
\citep{dao2022flashattention, ouyang2025kernelbench}.

This makes kernel generation an obvious target for language models, and the
field has moved quickly \citep{li2026cudal1, dai2026cudaagent}. The systems
considered here share a component and a blind spot. The component is a repair
loop: when a generated kernel fails, the error is returned to the model and
another attempt is requested, and this reliably raises benchmark scores. The
blind spot is what counts as failure. A kernel is judged by comparing its
output against a reference implementation on a few randomly drawn inputs, so a
kernel that is wrong in a way those inputs do not reach is recorded as correct.

One example shows what that allows. A PyTorch module is handed to a model,
which returns a CUDA kernel meant to replace it. The benchmark draws a few
random tensors, runs both versions, finds the outputs match, and records the
kernel as correct. Now give that kernel the same numbers arranged differently
in memory, as a slice of a larger tensor rather than a compact block. PyTorch
handles this without complaint. The kernel, which computed each memory address
by assuming the numbers were laid out end to end, reads the wrong elements and
returns the wrong answer. Nothing crashes and no error is printed. The
benchmark never tried that input, so its verdict does not change. This
dissertation calls such a kernel a \emph{silent failure}.

Put those two facts together and an uncomfortable possibility appears. If a
model is repeatedly asked to fix the failures a test can see, it may learn to
produce kernels whose failures the test cannot see, and the benchmark would
report progress either way.

This dissertation asks whether that happens. The question matters because a
kernel is a drop-in replacement for a component that already worked. A loud
failure costs an engineer an afternoon; a silent one returns plausible numbers
for as long as nobody checks.

\subsection{Aim and objectives}
\label{sec:aim}

The aim of this project is to determine whether iterative repair of
LLM-generated CUDA kernels improves their correctness, or merely conceals their
faults from the benchmark that scores them.

The objectives are:

\begin{enumerate}
\item Build a classifier that separates kernels which satisfy KernelBench's
correctness check from those which are correct under stronger testing, and
validate it against kernels of known category.
\item Design a stress battery of metamorphic probes that can be withheld from
the model, so that a repair loop cannot be optimised against it.
\item Measure the false-pass rate before and after repair, across several
models, both reasoning settings and two GPU architectures.
\item Determine whether repair changes how the benchmark ranks models.
\item Release the classified dataset and the analysis code so that every
reported number can be reproduced.
\end{enumerate}

This aim is narrower and sharper than the one in the original proposal, which
set out to build a general taxonomy of correctness failures. The taxonomy was
built, and it appears in Section~\ref{sec:taxonomy}, but it turned out to be a
means rather than an end: the interesting result was not the distribution of
failure types but the movement between them under repair. The aim is stated
here as the project actually developed.

\subsection{Terminology}
\label{sec:terminology}

Several terms in this report are either borrowed from software testing or
introduced here, and are used from Chapter~2 onwards. They are collected below
so that no definition arrives after its first use. The five failure categories
have their own table in Section~\ref{sec:taxonomy} and are not repeated here.

\begin{description}

\item[Reference module] The PyTorch implementation a generated kernel is asked
to replace. It defines what the kernel should compute, because no other
specification exists.

\item[Oracle] The procedure that decides whether a test has revealed a fault;
KernelBench's oracle compares outputs on five random inputs. Every oracle is
incomplete, because it can only inspect the inputs it is given.

\item[Probe, stress battery] A probe transforms the input, runs both the
reference module and the candidate on the result, and reports whether they
still agree. The battery is the full set of probes, run only after a kernel has
satisfied KernelBench's own check.

\item[Arm] One of the two experimental conditions: \emph{think} with reasoning
enabled, \emph{direct} with the same model and prompt and reasoning disabled.

\item[Turn, chain] A turn is one request to the model, turn~0 being the first
attempt and turns 1 to 3 repairs. A chain is the sequence of turns for one
problem, in one arm, on one GPU.

\item[Visible failure] A failure KernelBench can see, namely
\texttt{syntactic}, \texttt{runtime} or \texttt{functional}; these are the
failures reported back during repair.

\item[Silent failure] A kernel that satisfies KernelBench's check and is
nonetheless wrong, because a probe disagrees with the reference module.

\item[Relocation] A repair turn that converts a visible failure into a silent
one. The benchmark records it as a successful repair, because the failure it
could see has gone.

\end{description}

\subsection{Contributions}

Chapter~2 reviews how kernel generation is evaluated and how repair loops are
used, and closes in Section~\ref{sec:gap} with the gap this work addresses:
repair loops are optimised against a correctness check known to be incomplete,
and no published work measures what repair does to the kernels that survive it.
Addressing that gap, this project makes the following contributions.

\textbf{1. A withheld stress battery for generated kernels.} KernelBench's
correctness check is extended with seven kinds of probe over memory layout,
magnitude, dtype and repeated execution, and their results are kept out of
the repair prompt so that the model cannot fit them.

\textbf{2. Evidence that repair relocates failures.} Across three models and
two GPU architectures, iterative repair raises the acceptance rate while also
increasing the share of accepted kernels that are silent failures. Of the 244 chains
that repair turns into an apparent success, 79, almost one in three, are silent
failures.

\textbf{3. Evidence that repair reduces the benchmark's discriminating power.}
Under KernelBench's own contract the three models converge after repair to
between 91.5\% and 93.5\%, and no statistically significant pairwise difference
is detected, while the extended reading produces a wider spread and a different
ordering.

\textbf{4. A quantified account of where the effect comes from.} 85\% of silent
failures are caught by one relation, that a kernel must not change its answer
when the same values arrive through different strides. Because that relation
extends beyond KernelBench's stated contract, strict and extended correctness
are distinguished, and the two are compared directly where the distinction
changes a conclusion.

\textbf{5. An accompanying dataset and a reproducible analysis pipeline.} 2{,}852 classified
kernel attempts, 1{,}196 repair chains and the generated sources, from which
every figure and table in this report can be regenerated.

\subsection{Report structure}

Chapter~2 reviews how kernel generation is evaluated, why test suites define
correctness rather than measure it, and what is known about repair loops, and
ends with the gap this work fills. Chapter~3 sets out the experimental design,
the failure taxonomy, the stress battery and the repair loop. Chapter~4
describes the implementation and how it was validated. Chapter~5 reports the
results, Chapter~6 sets out the limitations, and Chapter~7 concludes.

\section{Literature Review}

\subsection{Writing code and checking it}

Large language models write useful code. Codex demonstrated this first, and it
also fixed how the field measures success: generate a program from a
description, run the tests that come with the task, and report the fraction
that pass \citep{chen2021codex}. That method works because the task carries its
own definition of correctness. The docstring states what the function should
do, and the tests check whether it does it.

CUDA kernels break this arrangement in two ways.

The task is set in PyTorch, a widely used machine learning framework
\citep{paszke2019pytorch}. A PyTorch module describes a computation
as a sequence of high-level operations, such as a convolution followed by an
activation, and the framework calls a library routine for each. Replacing that
module with a CUDA kernel means writing the same computation directly against
the GPU.

The first difficulty is widely recognised. A kernel is written against a particular memory
hierarchy and thread model, so good performance depends on hardware knowledge
that the source code never states \citep{kirk2012programming}. FlashAttention,
an attention kernel that reduces traffic between levels of GPU memory, required
years of expert effort \citep{dao2022flashattention}, and needed two further
years to reach a new generation of GPUs \citep{ouyang2025kernelbench}.

The second difficulty attracts less attention, and it is the subject of this
dissertation. A kernel has no docstring. It is not written against a
specification that a test can consult. It is written to replace an existing
PyTorch module, so the only available definition of correct is ``behaves like
that module''. Comparing two implementations on every possible input is
impossible. In practice somebody selects a small number of inputs and compares
the outputs on those.

The choice of inputs therefore decides what correctness means.

\subsection{How KernelBench decides that a kernel is correct}
\label{sec:evaluated}

KernelBench is the standard benchmark for this task
\citep{ouyang2025kernelbench}. It supplies 250 PyTorch modules across three
difficulty levels and asks the model to return an equivalent module built
around a custom CUDA kernel. It then reports $\mathrm{fast}_p$: the share of
generated kernels that are correct and at least $p$ times faster than PyTorch.
Frontier reasoning models beat the PyTorch baseline in fewer than 20\% of
cases, so the benchmark is far from solved.

The correctness half of that score rests on a single procedure. The authors
``evaluate on 5 random inputs per problem'', checking ``equivalence of output
between reference architecture \texttt{Model} and generated architecture with
custom kernel \texttt{ModelNew}''. In that notation \texttt{Model} is the
original PyTorch module and \texttt{ModelNew} is the generated replacement built
around a CUDA kernel. They are called the reference module and the candidate
throughout.

They explain the choice openly. Proving two programs equivalent is undecidable,
so they adopt random testing, which they describe as ``the most common
practical approach''. They argue that it suits this domain, because AI kernels
have simple control flow and ``the focus is primarily on numerical
correctness''. Five inputs are presented as ``a good tradeoff between the
ability to catch errors and efficiency''. To justify that number they ran an
experiment on 100 generated kernels, and found that kernels either passed
everything or failed everything: ``the 0/5 and 0/100 failures indicate that no
partial correctness was observed''.

That experiment is where the argument weakens. Every input in it shares one
shape and one memory layout, and only the values inside the tensors change. A
kernel whose fault depends on layout rather than on values will therefore pass
all five draws, and all one hundred. The absence of partial correctness follows
from the way the inputs were sampled. It is not evidence that five inputs are
sufficient.

Two recent papers approach this point without reaching it.
\citet{lange2025robustkbench} report that existing kernel benchmarks ``suffer
from exploitable loopholes and insufficient diversity in testing conditions'',
and respond with a stricter benchmark of their own. \citet{li2026cudabeaver}
show that a model can satisfy the tests ``with repair by degeneration,
simplifying the CUDA code into a safer but slower program''. Both establish
that the score can be gamed. Neither asks the simpler question: how often is
the score merely wrong?

\subsection{Tests do not measure correctness; they define it}
\label{sec:oracle}

Software engineering has a name for the difficulty reached at the end of the
last section. A test oracle ``determines whether a test execution reveals a
fault, often by comparing the observed program output to the expected
output'', and building a complete one is ``recognised as one of the fundamental
challenges of software testing'' \citep{segura2016metamorphic}. KernelBench's
five inputs are an oracle in exactly this sense. The useful question is not
whether the oracle is imperfect, since its authors say as much, but how much it
misses.

\citet{liu2023evalplus} measured that for Python. They took HumanEval and
increased its test cases by a factor of eighty, then re-evaluated 26 models on
the extended version. The additional tests caught ``significant amounts of
previously undetected wrong code'' and reduced pass@k by up to 19.3--28.9\%.

The more troubling result concerns the ranking. Two models that lost to ChatGPT
on the original benchmark defeated it on the extended one. A weak oracle does
not flatter every model by the same amount; it reorders them.

Metamorphic testing offers a disciplined way to add tests when the correct
answer is not known in advance. Instead of checking a single output, it
transforms the input and observes how the output ``morphs'' in response
\citep{segura2016metamorphic}. For a kernel offered as a drop-in replacement,
one such relation is almost too obvious to state: the same values, presented
through a different memory layout, must produce the same result. None of the
kernel benchmarks reviewed here applies it.

\citet{ludwig2026kaizen} show what happens when somebody applies it in a
neighbouring setting. Testing LLM-translated CUDA-to-OpenMP code, they found
faults in programs ``that compile and pass developer-written tests yet produce
incorrect scientific results'', and report that these faults ``are often
input-dependent''. Their subject is translation rather than generation, and
they use no repair loop, but the failure mode is the one measured here.

That failure mode already has a name outside software testing. Studies of large
server fleets describe corruptions in which ``the only symptom is an erroneous
computation'' \citep{hochschild2021cores}. The same word, silent, is adopted
here for a kernel that passes the benchmark and returns the wrong answer.

\subsection{Repair loops and the signal they learn from}
\label{sec:repair}

If a program fails, show the model the error and ask again.
\citet{chen2024selfdebug} formalised this idea, teaching a model to inspect
execution results and explain its own code, and reported improvements of up to
12\% on benchmarks that provide unit tests. \citet{madaan2023selfrefine}
generalised it to any task, using a single model as generator, critic and
reviser, and reported roughly 20\% absolute improvement across seven tasks.
Results of this kind are why repair is now a standard component rather than an
experiment.

Three later studies complicate the picture.

\citet{olausson2024selfrepair} charged repair its real cost. Each turn is
another model call, so the fair comparison is against simply drawing more
candidates. Judged that way, the gains are ``often modest, vary a lot between
subsets of the data, and are sometimes not present at all''. They locate the
reason in the feedback itself: repair is limited by ``the model's ability to
provide feedback on its own code'', and improves sharply when a stronger model
supplies that feedback.

\citet{huang2024cannot} go further. Without external feedback, models
``struggle to self-correct their responses'', and at times become worse. They
then explain where earlier positive results came from. Those experiments used
oracle labels to guide the correction, and ``the improvements vanish when
oracle labels are not available''.

\citet{brown2024monkeys} arrive at a compatible conclusion from a different
direction. Repeated sampling steadily raises the chance that some attempt is
correct, across four orders of magnitude. That coverage converts into real
performance only ``in domains like coding and formal proofs, where answers can
be automatically verified''.

Taken together, these three make one point. A repair loop can be no better than
the judge it answers to.

The kernel generation systems adopt repair without revisiting that judge.
CUDA-L1 rewards speedup through reinforcement learning, Astra runs several
agents through generation, testing and profiling, Kernel-Smith evolves a
population of candidates using ``structured execution feedback on compilation,
correctness, and speedup'', and CUDA Agent trains against ``automated
verification and profiling to provide reliable reward signals''
\citep{li2026cudal1, wei2025astra, cao2026ksearch, du2026kernelsmith,
dai2026cudaagent, chen2025cudallm}. Reasoning models, which work through
intermediate steps before answering \citep{wei2022cot}, perform best throughout.

Across these systems the feedback is the same short list: whether the code
compiled, whether it crashed, how fast it ran, and whether it matched the
reference on the standard inputs. None of them feeds back anything about memory
layout.

\subsection{The gap}
\label{sec:gap}

Two lines of work meet in this dissertation, and they have not met before.

The recent CUDA kernel systems reviewed here all repair, returning compiler
errors and failed comparisons to the model and asking again. Software testing has argued for
decades that such comparisons are incomplete oracles, and that adding tests to
a benchmark exposes code that was wrong from the start.

\citet{lange2025robustkbench} showed that KernelBench's oracle can be
exploited. \citet{li2026cudabeaver} showed that a model can satisfy it by
making the kernel worse. Neither measured what repair does to correctness
across several turns.

So the question remains unasked. When a model repairs its own kernel, does the
kernel become correct, or only harder to catch? That is what this project
measures.

\section{Design}

\subsection{Research design}

Section~\ref{sec:repair} ended with a prediction. A repair loop can be no
better than the judge it answers to, and every kernel system answers to a judge
that Section~\ref{sec:oracle} shows to be incomplete. This chapter describes an
experiment built to test that prediction.

Testing that prediction requires three things, and no existing harness provides
them together.

First, a correctness check stronger than the benchmark's. Without one, a wrong
kernel cannot be told from a right one.

Second, that stronger check must be hidden from the model. If the model can see
it, the model will repair against it.

Third, the same problem must be followed through a repair chain, with every
kernel version recorded, so that any change can be attributed to repair.

The design below provides all three. KernelBench's check is kept in form as the
benchmark's verdict, with one tightened tolerance that Section~\ref{sec:classifier}
states and Section~\ref{sec:limitations} returns to, a battery of further checks is added and never shown to
the model, and a repair loop runs driven only by that verdict, recording every
intermediate kernel.

KernelBench is used rather than a stricter benchmark such as
\texttt{robust-kbench} \citep{lange2025robustkbench} for the same reason. The
weak oracle is the object of study, not an obstacle to it, and replacing it
with a stronger one would remove the very thing whose consequences this work
measures.

One further control shapes the whole study. Comparing a reasoning model with a
non-reasoning model would confuse reasoning with everything else that differs
between two checkpoints: training data, size, tokeniser, alignment. This is
avoided by running two arms on the same model, using the same prompt and the
same temperature. The only difference is the \texttt{reasoning\_effort}
parameter, set to \texttt{high} in one arm and \texttt{none} in the other. The
extremes are used rather than intermediate settings so that the contrast is as
large as the parameter allows. This isolates the reasoning setting while
avoiding checkpoint-level confounds.

This contrast is stronger than the paired-checkpoint comparison used in most
earlier work. It is possible only because current models expose reasoning as a
runtime switch over fixed weights \citep{qwen2025qwen3}.

\subsection{A taxonomy of kernel failures}
\label{sec:taxonomy}

KernelBench reports one bit, correct or not, and that bit hides distinctions
which matter for diagnosis. Every generated kernel is therefore classified into one
of five categories, shown in Table~\ref{tab:taxonomy}.

The categories are ordered, and the first one that matches wins. This makes
each label deterministic, because a kernel that fails to build is never also
tested for numerical accuracy. The order runs from the most visible failure to
the least visible, which is also the order in which a developer would meet
them.

\texttt{pass}       & correct on the standard input and survives the battery \\
\bottomrule
\end{tabular}
\caption{The five failure categories. The first matching stage wins, so every

\texttt{silent} is the category this dissertation exists to measure. A silent
kernel compiles, runs, and agrees with the reference module on the inputs
KernelBench draws. Under KernelBench it is a success and counts towards
$\mathrm{fast}_p$, and it is nonetheless wrong.

The other four categories exist mainly so that \texttt{silent} can be separated
cleanly from them. The rest of this chapter explains how each label is
assigned.

Two further labels appear in the results and fall outside this taxonomy,
because they describe the attempt rather than the kernel: \texttt{empty} marks
a response that contained no code block, and \texttt{error} a fault in the
harness. Neither is counted as an accepted kernel, and together they account
for under 2\% of attempts.

\subsection{The classifier}
\label{sec:classifier}

The classifier runs a fixed sequence of stages. Algorithm~\ref{alg:classify}
gives the sequence, and the rest of this section explains three decisions
inside it.

\begin{algorithm}[H]
\caption{Classifying one generated kernel}
\label{alg:classify}
\begin{spacing}{1.0}
\begin{algorithmic}[1]
\State seed the generator; build the reference module from the problem
\State \textbf{compile} the generated source \Comment{Stage 1: does it build?}
\State \textbf{if} compilation fails \textbf{then return} \texttt{syntactic}
\State seed again; construct the candidate module with identical weights
\State run one forward pass on the standard input, then synchronise
  \Comment{Stage 2a: does it run?}
\State \textbf{if} it raises \textbf{then return} \texttt{runtime}
\State time one warm forward call \Comment{Stage 2b: can it be evaluated?}
\State \textbf{if} it exceeds the forward-time limit \textbf{then return} \texttt{runtime}
\State run \texttt{compute-sanitizer} \Comment{Stage 2c: does it violate memory?}
\State \textbf{if} a violation is reported \textbf{then return} \texttt{runtime}
\State compare candidate and reference output \Comment{Stage 3: right on the standard input?}
\State \textbf{if} they disagree \textbf{then return} \texttt{functional}
\State run the stress battery \Comment{Stage 4: right under stress?}
\State \textbf{if} any probe disagrees \textbf{then return} \texttt{silent}
\State \Return \texttt{pass}
\end{algorithmic}
\end{spacing}
\end{algorithm}

\textbf{Weight synchronisation.} Many Level 2 problems contain learnable
parameters. If the reference module and the candidate module are built from
different random draws, they hold different weights. Their outputs then differ
for reasons that have nothing to do with the kernel, and every kernel looks
wrong. Following KernelBench, the random generator is reseeded three times: before
the initialisation inputs are produced, before each module is constructed, and
before every input draw. The two modules then hold identical weights and see
identical data.

\textbf{A limit on forward time.} A full classification issues roughly ninety
forward calls, so a kernel taking tens of seconds per call cannot be evaluated
at all. Stage 2b times one warm call and labels such a kernel \texttt{runtime},
rather than letting it exhaust the container and disappear from the dataset
unlabelled. The call is timed warm because the first also pays for module
loading. The limit is raised on slower hardware, so that no kernel is rejected
merely for running on a slower device.

\textbf{The sanitizer stage did not run.} Stage 2c invokes NVIDIA's
\texttt{compute-sanitizer} to detect memory violations that do not crash the
program. The stage is implemented and is exercised by the validation suite, but
it reports that the device is unsupported on both GPUs available for this work,
so it contributed no labels to the results in Chapter~5. Races and non-crashing
out-of-bounds reads are therefore undetected throughout, and
Section~\ref{sec:limitations} returns to what that costs.

\textbf{A comparison tolerance.} Outputs are compared with an absolute and
relative tolerance of $10^{-3}$, applied recursively through tuples, lists and
dictionaries so that structured returns are handled. The tolerance is a real
choice: set it too tight and ordinary floating-point reassociation is reported
as a fault; set it too loose and a genuinely wrong kernel passes.

The value used here is tighter than the $10^{-2}$ that KernelBench states for
its own tasks. A kernel whose output differs from the reference by between the
two thresholds is therefore labelled \texttt{functional} here, while a standard
KernelBench harness would accept it. The acceptance rates in Chapter~5 are
consequently not identical to those KernelBench itself would report, and
Section~\ref{sec:limitations} returns to what that means.

\subsection{The stress battery}
\label{sec:battery}

The battery is the stronger oracle promised in the research design. Because it
carries the study's central measurement, it is worth restating plainly what it
is before the individual probes are described.

The battery is a fixed set of additional tests that runs only after a kernel has
already satisfied KernelBench's own check at stage 3. A kernel that fails
earlier never reaches it, so the battery is applied exactly to the population
the benchmark would have declared correct. Each test, called a probe, derives a
new input from the standard one, runs both the reference module and the
candidate on that input, and records whether the two still agree. A kernel that
survives every probe is labelled \texttt{pass}; a kernel that fails any probe is
labelled \texttt{silent}. The outcome is recorded but never shown to the model,
for the reason given in Section~\ref{sec:repairloop}.

Two properties of that design matter. Each probe presents inputs the standard
check never uses, and it compares the candidate against the reference on those
same inputs rather than against a stored expected answer. A probe can therefore
only fail when the two implementations disagree. The battery never holds its own
idea of the right answer, so it cannot punish a kernel for anything except
differing from the module it claims to replace. This also means the battery
inherits the reference module as its definition of correct: if PyTorch and the
kernel agree on a transformed input, the probe passes, whatever that answer
happens to be.

Each probe pairs a transformation of the input with a check on the output. The
transformations follow the metamorphic approach described by
\citet{segura2016metamorphic}, in which new test inputs are derived from an
existing one rather than invented from scratch. The check is differential: the
reference module and the candidate are both run on the transformed input, and
the candidate must agree with the reference. \citet{ludwig2026kaizen} combine
the same two techniques for translated HPC code.

The transformations differ in what they preserve, and the distinction matters.
Restriding a tensor, or repeating an identical call, leaves the correct output
unchanged, so those two probes are metamorphic relations in the strict sense:
the candidate must return exactly what it returned before. The remaining probes
change the input values, so the correct output changes with them, and the
invariant is only that the candidate continues to match the reference.
Table~\ref{tab:probes} lists the seven kinds of probe. They amount to nine
individual checks, because the fresh-draw probe is run three times. The seven
were chosen to cover the properties a kernel might silently depend on but which
the standard input merely happens to supply: the particular values drawn, their
layout in memory, their magnitude, their element type, and the absence of state
carried between calls. The set is not exhaustive, and
Section~\ref{sec:limitations} treats that as a limitation.

One probe deserves separate comment, because it dominates the results.
\texttt{non\_contig} builds a tensor holding exactly the same values as the
standard input, but presented through non-unit strides. It does this by
stacking the tensor with itself and taking one slice, a construction chosen
because it alters the strides while leaving the shape and every value
untouched; a transpose or a permutation would also reorder the data, which
would confound layout with order. A kernel that indexes raw
pointers, assuming a dense row-major layout, then reads the wrong elements and
returns a wrong answer. A kernel that calls \texttt{.contiguous()}, or respects
the strides it is given, returns the right one. KernelBench draws only
contiguous tensors, so this fault is invisible to it by construction.

Two rules keep the headline number honest.

The first is that a harness fault is never charged to the kernel. If a probe
raises because the machine ran out of memory, or because the harness itself
failed, the probe records \texttt{skipped} and the kernel is not condemned.
Otherwise a 16\,GB card would convert working kernels into silent failures
whenever memory ran short, and inflate the study's central measurement.

The second is that refusing a dtype is not failing it. A kernel is compiled
against a specific element type, so one written for 32-bit floats rejects
half-precision input before a single thread runs. That is the kernel enforcing
the contract it declared, not computing a wrong answer, so it is recorded as a
robustness flag rather than a silent failure.

\subsection{The repair loop}
\label{sec:repairloop}

After a failure the model is shown its own source and the actual error, and
asked again. The loop runs for up to three further turns. Three is a
compromise between giving repair a fair chance and spending model calls on
chains that will not recover, and the results justify it after the fact: of the
chains repair rescues, 59\% reach a passing kernel on the first repair turn and
only 14\% on the third, so a fourth turn would add little.

Only \texttt{syntactic}, \texttt{runtime}, \texttt{functional} and
\texttt{empty} are repairable, and \texttt{pass} and \texttt{silent} end the
chain. The feedback is deliberately plain: the compiler's own message, the
exception, or the reported numerical mismatch. Logs are truncated to their last 800
characters, because \texttt{nvcc} puts the decisive line last and the output
before it is largely repeated build commands.

The most important decision in this design is what the loop is \emph{not}
told.

Stage 4 never appears in the feedback. A silent kernel ends its chain in
exactly the way a passing kernel does, and the model is never told that a
stress probe disagreed.

This is not a convenience. \citet{huang2024cannot} show that reported gains
from self-correction came from oracle labels guiding the process, and that they
disappear once those labels are withdrawn. A battery fed back into the prompt
would be exactly such a label: the model would repair against it, the
false-pass rate would fall, and the fall would measure the model's skill at
fitting a held-out test rather than any improvement in correctness. Withholding
stage 4 keeps the battery an independent instrument. It also matches
deployment, since a developer running a repair loop against KernelBench sees
compiler errors and failed comparisons, not a stress battery.

\subsection{Experimental plan}

\textbf{Models.} Three models are evaluated: GLM-5, DeepSeek V3.2 and
Qwen3-235B-A22B (hereafter Qwen3-235B), each served through Amazon Bedrock.

Models were selected for experimental controllability rather than for benchmark
performance. The two-arm design needs a model whose reasoning can genuinely be
turned off, and this was tested rather than assumed. Several otherwise suitable
candidates continued to reason regardless of the parameter, and those were
rejected: their \texttt{direct} arm would silently have been a second
\texttt{think} arm, and the central contrast would have been empty. Among the
models that honoured the switch, the three chosen come from three different
developers, so a result common to all three is less likely to be a property of
one training pipeline.

Two further constraints shaped the choice, the first of which is cost. The
design issues
one model call per problem, per arm, per turn, which came to 1{,}448
generations and roughly 8.5 million tokens. Frontier proprietary models are
priced well above the open-weight models used here, and at this volume that gap
separates an experiment that can be run from one that cannot. The question under study is what a repair loop does to a benchmark
verdict, not which model writes the best kernels, so paying for the strongest
available models would have raised the cost without changing what is measured.

The second constraint is uniformity. Serving all three models through a single
provider means one client library, one prompt format and one set of parameters,
so no difference between models can be attributed to the harness. Proprietary
frontier models such as Claude and GPT were considered and set aside on both
grounds: each exposes reasoning through its own interface, which would have
introduced a second source of variation alongside the one under study, and each
is substantially more expensive per token at this scale. This restricts
generality, and it is stated here as a limitation. The findings apply to models that
expose reasoning as a runtime switch.

\textbf{Tasks.} KernelBench Level 2, the fusion tier, in which several PyTorch
operators must be combined into one kernel. Level 1 is excluded because
single-operator problems are largely solved and produce too few failures to
analyse. Level 3 is excluded for time, and Section~\ref{sec:limitations}
returns to that exclusion. All 100 Level 2 problems are used, so no sampling
decision can bias which failures are observed.

\textbf{Hardware.} Every problem runs on two GPUs: an Ada-generation L4 and a
Turing-generation T4. Both use one pinned CUDA image and one pinned set of
Python packages. Running both makes it possible to detect a kernel that passes
on one architecture and fails on another, and guards against a result that is
an artefact of a single device.

\textbf{Determinism.} Temperature is zero, and one sample is drawn per problem,
per arm, per turn. Each cell of the design is therefore a single greedy
generation. The design consequently measures no variation between repeated
generations of the same problem, and Section~\ref{sec:limitations} states what
this excludes. The benchmark dataset is pinned to one revision, so later upstream edits
cannot change what was run.

The full design is 3 models $\times$ 2 arms $\times$ 2 GPUs $\times$ 100
problems $\times$ 4 turns. It is evaluated lazily: a chain stops as soon as it
reaches \texttt{pass} or \texttt{silent}.

\subsection{Metrics and units of analysis}
\label{sec:metrics}

Three different quantities are easy to confuse, so each is named separately and
used consistently from here on.

\begin{description}
\item[Acceptance rate] The share of kernels KernelBench would report as
correct, which is the \texttt{pass} and \texttt{silent} categories together.
This is the number a standard harness prints.
\item[Full-battery pass rate] The share of kernels that satisfy KernelBench's
check \emph{and} survive every probe, which is the \texttt{pass} category
alone.
\item[False-pass rate] The share of accepted kernels that are silent, written
$\mathit{silent} / (\mathit{silent} + \mathit{pass})$. Equivalently, it is the
difference between the acceptance rate and the full-battery pass rate, divided
by the acceptance rate. It is the study's central measurement.
\end{description}

\textbf{Strict and extended correctness.} Repeated random draws and the
determinism check test only what KernelBench's contract already promises, so a
kernel failing them is wrong under any reading. The remaining probes, which
restride the input or change the magnitude or type of its values, go beyond
that contract. \emph{Strict} correctness condemns a kernel only on the first
group; \emph{extended} correctness, which treats the kernel as a drop-in
replacement, condemns it on either. Chapter~5 reports
false-pass rates under the extended reading, and compares the two readings
directly where the distinction changes a conclusion, in
Section~\ref{sec:ranking}.

\textbf{Unit of analysis.} A \emph{chain} is one problem attempted by one model
in one arm on one device, and contains up to four \emph{attempts}, one per
turn. Rates are computed over chains, using the first attempt for a one-shot
figure and the last for a post-repair figure. Where the two GPUs are pooled
each problem contributes twice, so pooled and per-device results are reported
separately.

\textbf{Statistical tests.} McNemar's test compares two models over the same
problems, because those observations are paired. Fisher's exact test compares
two disjoint sets of kernels, those accepted at the first attempt against those
repair made acceptable. A bootstrap over problems gives an
interval for a single rate. None of these measures variation between repeated
generations, which the design does not capture.

\subsection{Execution environment}

Generated code is untrusted. A model asked for a CUDA kernel can return
anything, and that code is compiled and executed. Each classification therefore
runs on Modal in a container, an isolated environment with its own filesystem,
that is used once and then destroyed. The network is blocked and access to
other resources in the account is withdrawn, so a generated kernel can reach
nothing outside its own container and cannot affect the next one.

Reproducibility requires the environment to be fixed rather than merely
described. Every run used CUDA 12.4 with the same pinned Python packages, and
the environment is identified by a cryptographic digest rather than by a
version label, so that a later rebuild cannot silently substitute different
software. The Python packages are pinned
to exact versions: \texttt{torch==2.6.0}, \texttt{ninja==1.11.1.1},
\texttt{openai==2.41.1}, \texttt{datasets==5.0.0} and \texttt{modal==1.5.0}.
The KernelBench dataset is pinned to one revision, so a later upstream edit
cannot silently change the problems.

One setting affects the numbers directly. TF32 arithmetic is disabled for both
matrix multiplication and cuDNN, because it reduces precision differently
between GPU generations and would otherwise confound the comparison in
Section~\ref{sec:crossgpu}. With it disabled, a numerical disagreement is
attributable to the kernel rather than to the hardware.

\subsection{Caching and provenance}

Generations and classifications are cached under independent keys, so a change
to the classifier can be applied to kernels already generated. The generation
key identifies the request to the model and excludes the GPU, which is why one
kernel can be classified on both devices without being generated twice.

One principle governs both keys: \emph{a field that decides an outcome must be
part of the key}. The forward-time limit is the clearest case, since it decides
whether a slow kernel is labelled \texttt{runtime} or proceeds to the battery.
Each record also carries the version of the classifier that produced it, so
results from a superseded version can be excluded, as
Section~\ref{sec:validation} describes.

\subsection{Validation}
\label{sec:validation}

A classifier that assigns the wrong label produces confident and worthless
results, so validation runs at two levels. The first is a suite of unit tests
over the pure logic, needing no GPU, covering selection and deduplication,
chain outcomes, the rate calculations, the dtype and out-of-memory rules in the
battery, the repair policy and the cache keys. The second is known-answer
validation: eleven
hand-written kernels of known category are run through the real classifier on
real hardware, covering correct kernels with weights, mutating inputs,
structured returns and nested inputs, plus one kernel each for the four failure
categories and one that is correct but too slow. The silent case is right on
contiguous input and wrong on strided input, so it exercises the probe the
results depend on most. The check asserts the category and, where it matters,
the failing stage, since \texttt{runtime} is reachable several ways.

This layer earned its cost: four defects were found that would each have
corrupted the headline number, and all four had passed the unit tests.

The most serious was silent in the strict sense: the routine that copies
tensors preserved their values but not their strides, so the
\texttt{non\_contig} probe was handing the kernel a contiguous tensor and
testing nothing. Every false-pass rate measured before the fix was measured
with the study's main probe disabled. The second was its opposite, an
\texttt{fp16} probe that reported a crash on every passing kernel, from which
the rule in Section~\ref{sec:battery} follows: a probe firing on 100\% of cases
measures the harness. The third was environmental, a setting that failed to
reach the container, leaving 70 records labelled with the wrong device; the fix
was to read the device name on the GPU itself. The fourth was a missing reseed,
so reference and candidate held different weights on any problem with learnable
parameters and every kernel looked wrong.

\subsection{Reproducibility}

No figure or table in this report contains a hand-copied number. Every result
derives from two exported tables, one row per classified kernel and one row per
repair chain, together with the generated kernel sources. The code was developed
under Git version control, and the code, the exported tables and the kernel
sources are submitted alongside this report as a single archive.

Two kinds of reproducibility should be distinguished. The analysis is exactly
reproducible: re-running the scripts over the submitted tables reproduces every
figure and table here, and does so without access to a GPU, but the generations
are not. Temperature is zero, so the model was asked for a deterministic response,
but the provider serves one model through an alias that is repointed to newer
checkpoints over time, and the pipeline did not record which checkpoint
answered. Repeating the generation step at a later date may therefore query a
different model.

In the reasoning arm the false-pass rate rises for all three models, by between
2.4 and 5.7 points. Figure~\ref{fig:relocation} shows the movement directly.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.9\linewidth]{figures/fig1_relocation.pdf}
\caption{Repair raises the acceptance rate and the false-pass rate together.
Every model moves upward, so a harness that reports only the acceptance rate
records this as unambiguous improvement.}
\label{fig:relocation}
\end{figure}

The direct arm is less consistent and carries correspondingly less weight.
GLM-5 and DeepSeek V3.2 rise as expected, but Qwen3-235B falls, from 85.2\% to
67.4\%. The fall is arithmetic rather than a reversal of the effect. With
reasoning disabled, Qwen3-235B produced only 27 accepted kernels at the first
attempt, of which 23 were silent. Repair then added ten genuine passes and six
further silent failures, so the count of silent kernels rose while the
proportion fell. Rates computed over so few kernels move sharply on a handful
of problems, which is why the direct arm is not used to support the
argument.

The mechanism is visible in the chains themselves. Counting outcomes across all
1{,}196 chains, repair rescued 165 chains to a genuine pass and converted
\textbf{79 chains from a visible failure into a silent one}, which are the
relocations. Combining the two gives the number a benchmark would report:

\begin{quote}
Repair produced 244 chains that KernelBench scores as a success, of which 79,
\textbf{almost one in three}, are silent failures.
\end{quote}

The effect is not confined to one model. It appears in GLM-5 (32 chains),
DeepSeek V3.2 (33) and Qwen3-235B (14), and splits evenly across the two GPUs.

This comparison can be tested directly. Repair produces a set of accepted
kernels that is disjoint from the set accepted on the first attempt,
so the two can be compared without the shifting denominators that make a
before-and-after rate awkward. Fisher's exact test is used because the outcome is
binary and some cells are small enough that a chi-squared approximation would be
unreliable. The unit of observation is one chain, meaning one problem attempted
by one model in one arm on one device. The pooled analysis treats chains as
independent, and because problem identities recur across models and devices the
pooled values should be read cautiously; per-model and per-device results are
reported alongside them. If repair produced work of the same quality as a
first attempt, the share of silent failures would be the same in both groups,
and it is not. In the reasoning arm, 12.4\% of first-attempt acceptances are silent
against 25.7\% of repair-produced ones, and Fisher's exact test gives
$p = 0.0002$. Pooling the two GPUs counts each problem twice, so the test was
also run on each device alone, where it holds independently at $p = 0.0058$ on the
L4 and $p = 0.0089$ on the T4. Per model the result is significant for GLM-5
($p = 0.0021$) and Qwen3-235B ($p = 0.0301$) but not for DeepSeek V3.2
($p = 0.4567$), whose first attempts were already unusually often silent.

Bootstrapping over the 100 problems gives the false-pass rate itself an
interval, and those intervals are wide: 14.6\% [6.8, 23.4] rising to 20.3\%
[12.5, 28.7] for GLM-5, with similar overlap for the other two models. The rise
within any single model is therefore not established on its own. The claim this
work makes is the one the Fisher tests support, that \emph{the kernels repair
produces are more often silently wrong than the kernels accepted on the first
attempt}.
Figure~\ref{fig:outcomes} breaks the chains down by outcome.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.92\linewidth]{figures/fig2_repair_outcomes.pdf}
\caption{Repair chain outcomes. \emph{Rescued} chains end in a genuine pass and
\emph{hidden} chains end in a silent failure that began as a visible one. Both
are recorded as repair successes by a standard harness.}
\label{fig:outcomes}
\end{figure}

A typical relocation is unremarkable to look at. On Level 2 problem 22,
DeepSeek V3.2 begins with a trivial and very loud failure, an undefined name
because a Python module was never imported, and returns one turn later with a
kernel that builds, runs, matches the reference on the standard input, and
disagrees with it on a strided one. The same sequence occurs on both GPUs.
Nearly two thirds of all relocations, 47 of 79, complete in a single turn like
this. The model was told only that a name was undefined. It fixed exactly that,
and in rewriting the kernel introduced an assumption about memory layout that
nothing in its feedback could contradict.

This is the behaviour that Section~\ref{sec:repair} predicted.
\citet{olausson2024selfrepair} argue that repair is bounded by the quality of
the feedback the model receives, and the feedback here contains no information
about layout. \citet{huang2024cannot} argue that improvement measured against a
signal the model can see is not evidence of correctness. The stress battery is
withheld precisely so that the measurement survives, and what it shows is that
a substantial part of repair's apparent benefit is the disappearance of
evidence rather than the repair of a fault.

\subsection{Repair and model ranking}
\label{sec:ranking}

\citet{liu2023evalplus} found that an insufficient test suite does not merely
depress scores; it reorders models. The same effect appears here, and repair
causes it.

Table~\ref{tab:ranking} compares the two readings defined in
Section~\ref{sec:terminology}. Under the strict reading a kernel is condemned
only if it violates KernelBench's own contract. Under the extended reading any
probe may condemn it.

\bottomrule

The two readings disagree about the order. Under the strict reading
Qwen3-235B places last; under the extended reading it leads by eight points.
The disagreement is created by repair, since at turn~0 both readings place
Qwen3-235B first. The ordering under the extended reading is consistent across
both GPUs but is established statistically only when they are pooled, so the
reliable claim is that the two readings cease to agree, not that one particular
order is correct.

The strict column also loses its ability to separate the models. After three
repair turns all three sit between 91.5\% and 93.5\%, and McNemar's test detects
no significant difference in any pair, with $p > 0.52$ throughout. This
is a failure to detect a difference rather than evidence that none exists. The
unit of pairing here is one problem on one device, since the two models being
compared attempted exactly the same problems on exactly the same hardware. Under the extended reading Qwen3-235B is ahead of both others with
$p = 0.037$ when the two GPUs are pooled. That pooling treats the devices as
independent when they are not, and the per-device tests give $p$ between 0.12
and 0.23, so the ordering is consistent rather than established. The strict
result, that no pairwise difference is detected at all, is the firmer half and
needs no such qualification.

Repair therefore does more than inflate the benchmark. It compresses the strict
rates into a narrow band of 91.5\% to 93.5\% in which no pairwise difference is
detected, while the extended reading produces a wider spread and a different
ordering.

\subsection{Which probe does the work}
\label{sec:probes}

The battery is not uniformly responsible for these results.
Figure~\ref{fig:probes} attributes the 172 silent attempts to the probes that
caught them.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.88\linewidth]{figures/fig4_probes.pdf}
\caption{Attribution of silent failures to probes. One probe dominates.}
\label{fig:probes}
\end{figure}

The non-contiguous probe is involved in 158 of the 172 silent attempts, and is
the \emph{only} probe that fires in 146 of them, or 85\%. The extreme-value
probe accounts for most of the remainder at 21 attempts. The small-magnitude,
zero and repeated-draw probes contribute almost nothing.

This is the strongest objection to the work, since the headline finding rests
largely on a single relation. Two pieces of evidence suggest the probe is
discriminating rather than a blanket penalty: it is passed by the large
majority of generated kernels, and the fix is one line, since a kernel that
calls \texttt{.contiguous()} on its inputs satisfies it, which some models
already do unprompted.

A plausible alternative interpretation remains available: kernels that assume
contiguity comply with KernelBench's stated contract, which promises only
contiguous inputs. Section~\ref{sec:ranking} therefore compares the strict and
extended readings directly, and Section~\ref{sec:limitations} treats the
dependency as a threat to validity rather than a detail.

\subsection{Cross-GPU divergence}
\label{sec:crossgpu}

Running every kernel on two GPU generations allows a further question: does the
same kernel behave differently on different hardware?

Of the 1{,}404 kernels classified on both an L4 and a T4, 55 received different
labels. Almost all are reshuffles among visible failures, such as a kernel that
crashes on one device and returns a wrong answer on the other. Nine involve a
harness fault rather than the kernel.

One pair looked like the case of real interest, passing on one device and
failing silently on the other. On inspection it was not. Every check that could
run had been skipped for lack of memory on the 16\,GB T4, so the battery never
ran at all.

\textbf{No evidence of architecture-specific silent failure was observed between
the L4 and the T4 in this dataset.} A hardware artefact is therefore an
unlikely explanation for the false-pass rates reported above. Two architectures
cannot establish device independence in general.

\subsection{Performance of passing kernels}

The last question is whether the kernels that survive are worth having.
Figure~\ref{fig:speedup} shows the distribution of speedups over PyTorch for
passing kernels.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.9\linewidth]{figures/fig5_speedup.pdf}
\caption{Speedup over the PyTorch baseline for kernels that pass the full
battery. The median gain is small for every model.}
\label{fig:speedup}
\end{figure}

The gains are modest: median speedups of 1.14$\times$ for GLM-5, 1.08$\times$
for DeepSeek V3.2 and 1.04$\times$ for Qwen3-235B. Between 76\% and 83\% of
passing kernels achieve any speedup over PyTorch.

There is a further pattern in those numbers. Qwen3-235B has the highest
observed full-battery pass rate and the lowest median speedup. This descriptive
pattern suggests a possible trade-off between correctness and speed.

One result must be reported separately, because it is a flaw in the benchmark
rather than a property of any model. Level 2 problem 80,
\texttt{80\_Gemm\_Max\_Subtract\_GELU}, is degenerate: its output is identically
zero for every input. GLM-5's reasoning arm proved this in a comment and
returned a zero tensor. That is a correct implementation of the specified
module, and it ran 2{,}671$\times$ faster than PyTorch on the L4 and
6{,}514$\times$ faster on the T4. The kernel implements the specification
correctly; the specification itself is degenerate.

This problem is excluded from the speedup statistics above. It is reported here
because a single degenerate task can move an average by a large amount, which
matters for anyone quoting KernelBench speedups.

\section{Limitations}
\label{sec:limitations}

\textbf{Scope.} The results cover KernelBench Level 2, three models that expose
reasoning as a runtime switch, and two GPU architectures. They therefore speak
to operator fusion rather than to whole network architectures, and to models
whose reasoning can be disabled without changing weights.

\textbf{The battery is itself an incomplete oracle.} The criticism this work
makes of KernelBench applies to the battery as well. It applies seven kinds of
transformation, and a kernel whose fault appears only under some other
transformation is recorded as passing. The reported false-pass rates are
therefore lower bounds, the failures a fixed battery detects, rather than
estimates of how many accepted kernels are wrong. The observed increase shows that a fixed battery detects
more silent failures after repair; the true rate remains unknown.

\textbf{One relation carries most of the result.} The non-contiguous probe
accounts for 85\% of silent failures on its own. Kernels that assume contiguity
comply with the contract KernelBench states, so Section~\ref{sec:ranking}
reports the two readings side by side. They disagree about the magnitude of the
effect and agree about its direction.

\textbf{Design choices bound the evidence.} One greedy sample per cell measures
no variation between repeated generations of the same kernel, so the claims
made are those the paired and disjoint-set comparisons in
Sections~\ref{sec:relocation} and~\ref{sec:ranking} support. The sanitizer
stage is implemented and validated but unsupported on the GPUs available, so
memory faults that do not crash the program fall outside these results.
Relocation is established for one repair configuration, three turns driven by
compiler-level feedback, which is the configuration in common use. Finally, the
comparison tolerance is tighter than the one KernelBench states, so a kernel
differing by between the two thresholds is counted here as a visible failure
rather than an accepted one. Such kernels never reach the battery, and the
direction of the resulting effect on the false-pass rate is not determined.

\section{Conclusion}

\subsection{Summary of findings}

Repair works by the measure the field uses, and that measure becomes
untrustworthy once repair has been applied.

Across 2{,}852 classified kernel attempts, repair raised the acceptance rate for
every model in every condition, by as much as 43 points, and raised the
false-pass rate alongside it. In the reasoning arm, the share of accepted
kernels that fail the stress battery rose from 14.6\% to 20.3\% for GLM-5, from
17.2\% to 19.6\% for DeepSeek V3.2, and from 7.0\% to 9.8\% for Qwen3-235B.

Counting chains rather than rates makes the effect plainer: of the 244 chains
repair converted into a benchmark success, 79 ended as silent failures. The
kernels repair makes acceptable are silently wrong more than twice as often as
those accepted at the first attempt, 25.7\% against 12.4\%, and that holds on
each GPU separately.

The mechanism is straightforward. A repair loop returns compiler errors,
crashes and failed comparisons, and nothing at all about memory layout, so the
model fixes what it is shown. In a typical case a kernel fails with
an undefined name, and returns one turn later building, running, matching the
reference on the standard input, and disagreeing with it on a strided one. Both
\citet{olausson2024selfrepair} and \citet{huang2024cannot} predict this
behaviour; what this work adds is the measurement.

A second result follows. After repair the three models sit between 91.5\% and
93.5\% under KernelBench's own contract, and no pairwise test detects a
difference between them. Under the extended reading the spread is wider and the
order is different. Repair does not only inflate the score;
it reduces the benchmark's ability to tell the models apart.

\subsection{Against the objectives}

The classifier and the withheld battery were built and validated, meeting
objectives~1 and~2. Validation against eleven known-answer kernels caught four
defects that would each have corrupted the headline number, including one that
had silently disabled the study's principal probe. The dataset, kernel sources
and analysis scripts are submitted alongside this report, meeting objective~5,
and no figure or table in this report contains a hand-copied number.

Objective~3 was met, and produced the central result. Every Level 2 problem was
run for three models, in two arms, on two architectures, yielding 1{,}196 of a
possible 1{,}200 chains, and the false-pass rate rises under repair for every
model in the reasoning arm.

Objective~4 was met with one qualification. The observed ranking changes after
repair, and repair is what causes the change, since both readings agree at
turn~0. Under the strict reading no
pairwise difference is detected, at $p > 0.52$ in every pair. Which model leads under the extended reading is
consistent across both GPUs but reaches significance only when they are pooled,
so it is reported as a direction rather than a settled order.

The aim set out in Section~\ref{sec:aim} can therefore be answered. Repair
improves benchmark scores, and part of that improvement is the disappearance of
evidence rather than the correction of a fault. A repaired kernel is not
reliably more correct; it is reliably harder to catch.

\subsection{Future work}

\textbf{Repeated-generation variability.} Drawing several samples per problem at
a non-zero temperature would add the dimension the present design does not
measure. Applied to one model it would quantify how much output varies between
attempts; applied to all three it would quantify the stability and uncertainty
of the observed ranking. It requires no new code.

\textbf{Reveal the battery deliberately.} This study withholds stage 4 so that
the measurement survives. The inverse experiment is well defined: expose the
battery and count the turns a model needs to satisfy it. A false-pass rate that
collapses within one or two turns would quantify how quickly any fixed oracle
can be fitted.

\textbf{A second number for kernel benchmarks.} The practical consequence of
this work is small and easy to adopt. A kernel benchmark that reports only an
acceptance rate cannot distinguish a repaired kernel from a concealed failure.
Reporting alongside it the share of accepted kernels that survive a stress
battery would make that difference visible at negligible cost.

\section{Generation and Repair Prompts}
\label{app:prompts}

\subsection*{One-shot generation}

The generation prompt is KernelBench's own one-shot CUDA prompt at FP32
precision, reproduced so that results remain comparable with published
KernelBench pass rates. It is assembled in four parts: the problem statement
below, a worked example consisting of an element-wise addition module and its
CUDA replacement, the reference module for the problem being attempted, and the
closing instruction. The worked example is KernelBench's and is not reproduced
here.

\begin{quote}\small
You write custom CUDA operators to replace the pytorch operators in the given
architecture to get speedups.

You have complete freedom to choose the set of operators you want to replace.
You may make the decision to replace some operators with custom CUDA operators
and leave others unchanged. You may replace multiple operators with custom
implementations, consider operator fusion opportunities (combining multiple
operators into a single kernel, for example, combining matmul+relu), or
algorithmic changes (such as online softmax). You are only limited by your
imagination.
\end{quote}

After the worked example and the reference module, the prompt closes with:

\begin{quote}\small
Note: The kernels should be optimized for FP32 (32-bit floating point)
precision.

Optimize the architecture named Model with custom CUDA operators! Name your
optimized output architecture ModelNew. Output the new code in codeblocks.
Please generate real code, NOT pseudocode, make sure the code compiles and is
fully functional. Just output the new model code, no other text, and NO testing
code!
\end{quote}

\subsection*{Repair}

A repair turn restates the whole generation prompt, appends the failed attempt,
appends the feedback for its category, and closes with a fixed instruction. The
feedback is the only part that varies between turns.

\begin{quote}\small
\textit{[the full generation prompt above]}

You already tried this, and it failed:

\textit{[the previous attempt, verbatim, inside a fenced Python code block]}

\textit{[category feedback, below]}

Fix the problem and output the complete corrected ModelNew code in one code
block. No explanation, no testing code.
\end{quote}

\subsection*{Category feedback}

For \texttt{syntactic}, \texttt{runtime} and \texttt{functional} the feedback
names the category and the failing stage, then quotes the compiler message, the
exception or the reported mismatch, truncated to the last 800 characters
because \texttt{nvcc} places the decisive line last. A memory-violation excerpt
from \texttt{compute-sanitizer} is appended when one is available.

\begin{quote}\small
Your previous kernel failed at stage: \textit{[category]}\\
Failing step: \textit{[stage]}\\
Build error: / Runtime error: / Output did not match the reference:\\
\textit{[message tail]}
\end{quote}

Two cases carry a written explanation instead, because the stored message is
the harness's own and says nothing the model can act on. A kernel killed by the
classification time limit is told that it did not finish, that the limit covers
compilation plus roughly ninety forward calls, and that the cause is either a
hang or a kernel too slow to measure; it is then asked to check every loop
bound, to ensure all threads reach any \texttt{\_\_syncthreads()}, and not to
serialise work onto one thread. A kernel rejected by the forward-time limit of
Stage~2b is given its measured time, told that the logic may be sound and the
speed is the problem, and asked to use more parallelism, coalesce global memory
accesses and avoid per-thread loops over large dimensions.

An empty response receives only: \emph{Your previous answer contained no code
block.}

No feedback is generated for \texttt{silent} or \texttt{pass}, which end the
chain. This is the withholding described in Section~\ref{sec:repairloop}: a kernel
judged silent is never told that a probe disagreed.
